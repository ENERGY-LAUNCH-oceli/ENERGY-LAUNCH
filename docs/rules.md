# Правила проверок

Пороги и параметры хранятся только в `src/config/rules` – в коде проверок и интерфейсе чисел нет.
Метаданные правил – `src/engine/rules/catalog.ts`, реализация – `src/engine/{invoice,telemetry,control,dashboards}`.

## Версии наборов

| Версия | Что добавлено |
| --- | --- |
| 1.0.0 | Первоначальная модель (до сверки с ТЗ) |
| 1.1.0 | Этап 1 по ТЗ: 24 месяца, шаг 15 мин, MH-001…MH-012 |
| 1.2.0 | Этап 2 по ТЗ: object.json, полнота 99 % за 48 ч, актуальность 30 мин, TM-001…TM-011 |
| 1.3.0 | Этап 3: тесты через имитатор, CT-010…CT-016 |
| 1.4.0 | Этап 4: четыре блока, привязка к object_id, роли и приёмка, DB-010…DB-016 |
| **1.5.0** (действует) | Реальный набор: окно истории от точки проверки, исходное/валидированное значение, задержка публикации, событийные сигналы управления |

Правило объявляет `sinceRuleset` / `untilRuleset`. Сессия фиксируется на версии, с которой начата; созданные ранее
сессии продолжают работать на своей. Принудительно выбрать версию – `VITE_RULESET_VERSION`.

## Этап 1 – история счётчиков (invoice.csv)

Точка проверки `2026-11-05T10:00:00Z`, окно – 24 месяца до местной полуночи (Europe/Brussels).

| Правило | Проверка | Параметр |
| --- | --- | --- |
| MH-001 | Файл загружен, обязательные колонки есть | `meterHistory.fields[].required` |
| MH-002 | Покрыты 24 последовательных месяца; перечисляются недостающие | `periodMonths: 24` |
| MH-003 | Шаг 15 мин; другая частота не досоздаётся | `intervalMinutes: 15` |
| MH-004 | Полнота интервалов | `minCompletenessPct: 100` |
| MH-005 | Дубли временных меток | `maxDuplicates: 0` |
| MH-006 | Корректные ISO 8601 UTC метки | `maxInvalidTimestamps: 0` |
| MH-007 | Единицы (kWh / kW; Wh вместо kWh по отношению E/(\|P\|·Δt)) | `fields[].unit`, `unitRatioThreshold: 100` |
| MH-008 | Знаки: энергия ≥ 0, CA_injection ≤ 0 | `fields[].sign` |
| MH-009 | Пустые и некорректные значения (кроме задержки публикации 5 сут) | `publicationLagDays: 5`, `infoOnlyEmptyFields` |
| MH-010 | Исходное vs валидированное (предупреждение) | `validatedTolerancePct: 5` |
| MH-011 | EAN offtake/injection в паспорте: 18 цифр, контрольная цифра GS1, различны | `eanLength: 18` |
| MH-012 | Данные связаны с объектом: EAN в файле или запись `data_files.invoice` | – |

## Этап 2 – телеметрия (object.json + telemetry.csv)

| Правило | Проверка | Параметр |
| --- | --- | --- |
| TM-001 | Паспорт разобран; источник доступен (иначе – время последней успешной проверки) | – |
| TM-002 | Карта сигналов полна: Grid всегда, PV и Battery по каждому активу паспорта | `requiredGrid`, `requiredPv`, `requiredBattery` |
| TM-003 | Обязательные сигналы есть в данных; «нет связи» ≠ неисправность | – |
| TM-004 | Данные этого объекта и его активов (object_id, префиксы) | – |
| TM-005 | Последнее значение не старше 30 мин от точки проверки | `maxAgeMinutes: 30` |
| TM-006 | Полнота 15-мин потока за 48 ч по каждому сигналу | `minCompletenessPct: 99`, `windowHours: 48` |
| TM-007 | Единицы из имени колонки | – |
| TM-008 | Знаки и диапазоны (PV ≥ 0, SoC 0–100 %, \|P\| ≤ 5000 kW) | `maxAbsPowerKw`, `maxEnergyKwhPerInterval` |
| TM-009 | Метки времени ISO 8601 с зоной UTC | – |
| TM-010 | Правдоподобность (предупреждение) | `maxSocJumpPct: 40` |
| TM-011 | Сигналы батарей; Not Applicable без батареи в паспорте | – |

Сигналы `*.setpoint_sent/received` – событийные: проверяется наличие, не полнота и не актуальность.

## Этап 3 – тесты управления (только имитатор)

Успех команды – три события: **Sent → Received (≤ 5 с) → Responded** (фактическая мощность в допуске, удерживается,
не позже 60 с после приёма).

| Правило | Проверка | Параметр |
| --- | --- | --- |
| CT-010 | Команды только в тестовый контур (имитатор) | – |
| CT-011 | Команда отправлена | – |
| CT-012 | Принята контроллером | `ackTimeoutSec: 5` |
| CT-013 | Отклик фактической мощности | `responseWindowSec: 60`, `toleranceKw: 2`, `tolerancePct: 3` |
| CT-014 | Батарея: тест setpoint | `requireBatterySetpoint` |
| CT-015 | PV: ограничение выработки (Not Applicable без PV) | `requirePvCurtailment` |
| CT-016 | Корректность значений команд (предупреждение) | `minStepKw: 5` |

## Этап 4 – финальные дашборды

| Правило | Проверка |
| --- | --- |
| DB-010 | object_id панели, истории, паспорта, телеметрии, команд и приёмок совпадает |
| DB-011…DB-014 | Блоки «История учёта», «Текущие активы», «Управление», «Качество данных и статус запуска» корректны |

## Подтверждения

| Этап | Требование | Роль |
| --- | --- | --- |
| 1 | MH-CONF-OWNER | Владелец объекта |
| 2 | TM-CONF-ENGINEER | Инженер ввода в эксплуатацию |
| 3 | CT-CONF-ENGINEER, CT-CONF-DISPATCHER | Инженер, диспетчер |
| 4 | – (заменено приёмкой DB-016) | Ответственный за приёмку |

## Как добавить версию

1. Скопировать последний `ruleset.v1_X.ts` в новую версию, изменить `version` и параметры.
2. Для новых правил указать `sinceRuleset`, для выведенных – `untilRuleset` в каталоге правил.
3. Зарегистрировать версию в `RULESETS` (`src/config/rules/index.ts`), при необходимости сделать её `ACTIVE_RULESET`.
4. `npm test` – тест `rules-config` сверяет параметры правил с набором, где правило появилось.
