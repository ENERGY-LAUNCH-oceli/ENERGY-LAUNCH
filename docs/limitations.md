# Ограничения и предложение для пилота

## Известные ограничения прототипа

| Ограничение | Следствие | Что нужно для пилота |
| --- | --- | --- |
| Вход по логину и паролю есть, но обязателен только при `AUTH_REQUIRED=1`; без входа демо-роли переключаются в меню профиля | В демо-режиме пользователь выбирает роль сам; права проверяются в движке | SSO, роли из каталога организации, вход обязателен |
| Хранилище PostgreSQL – последнее сохранение побеждает | Два пользователя, одновременно меняющие один объект, перезапишут состояние друг друга (журнал аудита сохраняет действия обоих) | Блокировка по `revision`, учётные записи и серверная проверка прав |
| Этап 3 – только имитатор | Тестовые команды уходят в локальный имитатор; реальные `setpoint_sent/received` из telemetry.csv анализируются на этапе 2 (TM-010: расхождение команды и отклика) | Подключение к тестовому контуру с разрешения эксплуатирующей организации |
| `Configuration_file.json` хранится, но не обрабатывается (невалидный JSON) | Доп. функция «заполнение конфигурационного файла» не реализована | Согласовать схему файла |
| Пороги 99 % / 30 мин / 5 с / 60 с / пауза 10 с / допуск 2 кВт · 3 % – параметры демонстрации из ТЗ | Для другого класса объектов могут не подойти | Новая версия набора правил |
| Ручное время проверки не измерено | Метрика «сокращение медианного времени ≥ 30 %» не подтверждена: ΔT показывается «не измерено» | Инженер проходит 6 оценочных сценариев по ручному чек-листу (выгрузка на `/scenarios`) с секундомером на той же странице |
| Протокол формируется на клиенте как PDF A4 без электронной подписи | Документ не имеет электронной подписи и не является подписанным актом | Серверная генерация PDF с электронной подписью |
| Docker-образ и compose (nginx, api, postgres) собраны по описанию, но не проверялись на этой машине (Docker не установлен) | – | `docker compose up --build` в чистой среде |

## Допущения по реальному набору – подтвердить у кейсодержателей

| № | Допущение | Почему |
| --- | --- | --- |
| A-01 | Окно истории – 24 месяца до местной полуночи дня точки проверки (05.11.2026, Europe/Brussels) | История набора начинается 05.11.2024 00:00 местного; точка проверки – конец телеметрии |
| A-02 | Интервал считается присутствующим при исходном **или** валидированном значении | Валидированные значения пусты ~36 последних суток у всех объектов |
| A-03 | Пустоты последних 5 суток – задержка публикации: видны, не блокируют; пустые мощность и CA – информация | Исходные значения пусты 3–4 последних суток |
| A-04 | Сигналы управления на этапе 2 событийные: проверяется наличие | Значения появляются только при командах |
| A-05 | `Battery.setpoint_sent` обязателен в карте сигналов батареи | Сигнал есть в разделе 9 ТЗ |
| A-06 | Объекты набора стартуют с автоматических проверок этапа 1; подтверждения и переходы – люди | Статусы без подтверждения не присваиваются |

## Предложение для пилота

1. **Объём:** 3–5 реальных объектов одного оператора, полный цикл 4 этапов на исторических данных и тестовом контуре.
2. **Данные:** прямое получение invoice-выгрузок и телеметрии из систем оператора (API вместо файлов), версии и SHA-256 сохраняются как сейчас.
3. **Управление:** подключение к тестовому стенду контроллера только по письменному разрешению; транспорт остаётся
   за флагом с проверкой в движке, реальный контур по умолчанию запрещён.
4. **Метрики:** замер ручного чек-листа и прототипа на одних объектах (время, найденные препятствия, ложные завершения).
5. **Платформа:** сервер с журналом аудита только на добавление, SSO и ролями, экспорт протокола с подписью.
