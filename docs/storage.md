# Хранилище (PostgreSQL)

Приложение сохраняет объекты, ход запуска и журнал аудита в PostgreSQL через небольшой сервер `server/`.
Сервер только хранит данные: статусы этапов, проверки и блокировки вычисляет движок в приложении.

## Запуск

```bash
npm run api        # сервер хранилища: http://127.0.0.1:8787/api
npm run dev        # приложение: http://127.0.0.1:5173 (Vite проксирует /api на сервер)
```

Без `DATABASE_URL` сервер использует **встроенный PostgreSQL** (PGlite – тот же движок, собранный в WebAssembly) с
данными в папке `.data/pglite`. Ничего устанавливать не нужно. Чтобы работать с отдельным сервером PostgreSQL,
укажите в `.env` строку подключения (файл не коммитится):

```
DATABASE_URL=postgres://energy_launch:пароль@127.0.0.1:5432/energy_launch
```

Схема создаётся сама при старте сервера (миграции `server/migrations.ts`, таблица `schema_migrations`).
В Docker Compose – отдельный контейнер `postgres:17`, пароль `POSTGRES_PASSWORD` из `.env`.

Если сервер не запущен, приложение работает как раньше: объекты – в localStorage, ход запуска – до перезагрузки.
Где сейчас лежат данные, видно в левом нижнем углу («PostgreSQL · сохранено») и в Настройках → Хранилище.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | – | PostgreSQL; пусто – встроенный |
| `PGLITE_DIR` | `.data/pglite` | Папка встроенного PostgreSQL (`memory://` – в памяти, для тестов) |
| `API_HOST`, `API_PORT` | `127.0.0.1`, `8787` | Адрес сервера; по умолчанию не виден из сети |
| `VITE_STORAGE` | `auto` | `auto` – сервер, если доступен; `server` – только сервер; `browser` – без сервера (e2e) |
| `VITE_API_URL` | `/api` | Адрес API для приложения |

## Таблицы

| Таблица | Содержимое |
| --- | --- |
| `user_objects` | Объекты из формы «Новый объект» (паспорт в `data`) |
| `workspaces` | Состояние запуска объекта: `inputs` (версии загрузок, история проверок, команды, панель), `session` (этапы, блокеры, подтверждения), `audit_ids` – события журнала этого состояния по порядку; `revision` растёт при каждой записи |
| `audit_events` | Журнал аудита: каждое событие отдельной строкой (`action`, `actor`, `ts`, `object_id`, `session_id`, `stage_id`, полное событие в `event`). **Только добавление:** триггеры запрещают `UPDATE`, `DELETE` и `TRUNCATE` |
| `help_questions` | Вопросы помощнику по сайту: текст, найденный ответ, сколько раз спрашивали; в FAQ – только с ответом и без личных данных ([help.md](help.md)) |
| `schema_migrations` | Применённые миграции |

Документы хранятся в `json`, а не `jsonb`: `jsonb` переставляет ключи, а порядок важен (этапы сессии, снимки проверок).

## Как сохраняется

1. При старте приложение запрашивает `GET /api/state` и накладывает сохранённые состояния на исходный портфель
   (только для той же версии набора правил).
2. Каждое изменение текущего объекта (этап, загрузка, проверка, подтверждение, команда, панель) через 0,35 с
   уходит одним запросом `PUT /api/workspaces/:objectId`; в той же транзакции дописываются новые события журнала.
   Запросы одного объекта идут строго по очереди – старое состояние не перезапишет новое.
3. Если закрыть или обновить страницу, пока сохранение не закончено, браузер переспросит.
4. «Сбросить состояние» на обзоре удаляет сохранённые состояния; объекты и журнал аудита остаются.
   Удаление объекта удаляет его описание и состояние; записи журнала остаются.
5. Объекты, созданные до подключения сервера (только в браузере), при первом подключении переносятся на сервер.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/health` | Доступность и вид хранилища (`postgres` / `pglite`) |
| GET | `/api/state` | Объекты пользователя и сохранённые состояния с журналом |
| PUT / DELETE | `/api/objects/:id` | Сохранить / удалить объект пользователя |
| PUT | `/api/workspaces/:objectId` | Сохранить состояние объекта и дописать журнал |
| DELETE | `/api/workspaces` | Сбросить состояния всех объектов |
| POST / GET | `/api/audit` | Дописать события / прочитать журнал (`objectId`, `sessionId`, `limit`) |
| POST | `/api/help/ask` | Вопрос помощнику по сайту → ответ из базы знаний |
| GET | `/api/help/questions` | Вопросы пользователей для FAQ |

## Безопасность

- Значения передаются в SQL только параметрами (`$1`, `$2`…), идентификаторы проверяются по шаблону.
- Тела запросов проверяются Zod; принимается только `application/json` до 32 МБ; состояние чужого объекта
  и события другого объекта отклоняются.
- Запросы со сторонних сайтов (`Sec-Fetch-Site: cross-site`) отклоняются; CORS не включён.
- Строка подключения (с паролем) не пишется в журнал сервера; в ответах об ошибках – только общее сообщение.
- Аутентификации нет (как и во всём прототипе): сервер по умолчанию слушает только 127.0.0.1.
- Данные кейса 4 попадают в базу только как результаты разбора загруженных файлов. Для удаления копий после
  хакатона (ТЗ 4.3) удалите `.data/pglite` или том `pgdata` в Docker.

## Тесты

- `tests/server/api.test.ts` – API на настоящем движке PostgreSQL (PGlite в памяти): сохранение без изменения
  порядка ключей, журнал только на добавление (триггеры), сброс, удаление, отказ на некорректные запросы.
- `tests/integration/server-storage.test.ts` – приложение и процесс `node server/index.ts`: ход запуска переживает
  перезагрузку и открытие в другом браузере, сброс и удаление доходят до базы, перенос старых объектов,
  работа без сервера.
