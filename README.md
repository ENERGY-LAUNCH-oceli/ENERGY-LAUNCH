| | |

| **Кейс** | Кейс 4. Запуск энергетического объекта на платформе (паспорт OE-04) |

## Какую задачу решает

Сейчас готовность энергетического объекта к эксплуатации подтверждают по ручному чек-листу: долго, без единого
статуса, а причины задержки приходится выяснять вручную. ENERGY LAUNCH ведёт объект через четыре последовательных
этапа – **история счётчиков → телеметрия в реальном времени → тесты управления → финальные дашборды** – и на
каждом этапе показывает:

- статус, выведенный только из входных данных и версии правил (не «на глаз» и не по заявлению);
- препятствия с точным местом: интервалы и поля истории, актив и сигнал телеметрии, причина для управления и панели;
- следующее действие, которое снимет препятствие;
- журнал аудита: кто, когда, на каких данных и по какой версии правил принял решение – любое решение воспроизводится.

Управление реальным оборудованием исключено: команды этапа 3 уходят только в локальный имитатор.

## Что реализовано

- **Конечный автомат этапов** (`src/engine/state-machine`): этап нельзя завершить при незакрытом предыдущем,
  при невыполненных обязательных проверках или без подтверждений ответственных ролей. Изменение входных данных
  делает подтверждения устаревшими – этап перепроверяется.
- **Детерминированные проверки** по версионированному набору правил (`src/config/rules`, действует v1.6.0):
  - этап 1 – покрытие 24 месяцев официальной историей, шаг 15 мин, полнота, дубли, единицы, знаки, EAN (GS1);
  - этап 2 – карта сигналов из `object.json`, полнота ≥ 99 % за 48 ч, свежесть ≤ 30 мин, единицы, привязка к объекту;
  - этап 3 – тест каждого управляемого актива: команда отправлена → принята контроллером → актив откликнулся
    мощностью в ожидаемом интервале; пауза между командами (CT-017);
  - этап 4 – обязательные блоки панели, данные нужного объекта, права ролей, приёмка ответственным.
- **Загрузка данных**: `invoice.csv`, `telemetry.csv`, `object.json` по этапам или «брось файл куда угодно» –
  тип и объект определяются по содержимому. Реальный набор кейса (Building1–6) разбирается в Web Worker потоково.
- **Роли и права** – инженер запуска, оператор, ответственный за приёмку; права проверяются в движке, отказ пишется
  в журнал. Вход по логину и паролю, личный кабинет и админ-панель – при работе с сервером.
- **Журнал и протокол**: сквозной журнал с воспроизведением статуса на момент записи, выгрузка журнала объекта
  в JSON и CSV, протокол готовности с экспортом в PDF.
- **11 сценариев ТЗ** (`/scenarios`) – каждый в своей песочнице через настоящие проверки и переходы; метрики
  качества (верность статусов, полнота препятствий, ложные завершения, подтверждения) и сравнение с ручной
  проверкой по формуле ТЗ (ΔT по медианам, секундомер, ручной чек-лист из каталога правил).
- **Помощь в исправлении**: для провалившейся проверки – данные объекта, варианты исправления (новая версия паспорта,
  текст запроса поставщику данных, тестовые команды в имитатор) и тур «Показать на сайте».
- **Обучение** (`/help`): уроки и туры по каждому блоку, FAQ, помощник по сайту без внешних ИИ-сервисов.
- **Хранилище**: PostgreSQL через API сервера (без `DATABASE_URL` – встроенный PGlite); несколько вкладок и
  пользователей – ревизии, устаревшая запись отклоняется (409). Без сервера – работа в браузере.
- **Эксплуатация**: Docker (nginx со строгой CSP, API, PostgreSQL), страницы состояния HTTP и «Нет подключения».

## Как запустить

Требуется Node.js ≥ 20.19 (проверено на 22).

```bash
npm ci
npm run dev        # http://127.0.0.1:5173 – вместе с сервером хранилища (без DATABASE_URL – встроенный PostgreSQL в .data/)
```

Без набора кейса приложение работает на синтетическом демо-портфеле (6 объектов). Как подключить реальный набор
(Building1–6) – [docs/data-upload.md](docs/data-upload.md). Принудительно синтетика: `VITE_DATASET=synthetic npm run dev`.

Сервер хранилища встроен в dev-сервер; отдельно его можно запустить `npm run api` (127.0.0.1:8787) – тогда
`npm run dev` использует его. Без сервера приложение тоже работает, но ход запуска хранится только до перезагрузки
страницы. Хранилище, таблицы и API – [docs/storage.md](docs/storage.md).

Демо-стенд https://elaunch.xroyse.ru – набор кейса 4 (публикацию разрешил владелец данных); раскладка и обновление –
[docs/deploy.md](docs/deploy.md).

### Docker

```bash
cp .env.example .env        # задайте POSTGRES_PASSWORD (в репозиторий не попадает)
docker compose up --build   # http://127.0.0.1:8080
```

Три контейнера: `energy-launch` (SPA через nginx, строгая CSP, без карт исходников; `/api` проксируется),
`api` (сервер хранилища) и `db` (PostgreSQL 17, том `pgdata`). Данные кейса в образ не входят:
`public/case4` монтируется томом только для чтения. Без папки – синтетические данные.
Проверка запущенных контейнеров – `bash scripts/docker-smoke.sh` (заголовки безопасности, API через nginx, страницы
состояния, данных кейса нет в образе). В CI то же делает `.github/workflows/docker.yml`.

## Основной сценарий проверки

**Полный путь объекта до готовности** (синтетический портфель, `/objects/obj-001/launch`, в селекторе
«Демонстрационный сценарий» – «Успешный запуск»):

1. Этапы 1–3 по очереди: «Начать этап» → «Запустить проверки» → «Подтвердить требования» → «Завершить этап».
2. Этап 4: «Дашборды» → «Конструктор» → «Опубликовать v1».
3. Меню профиля → роль «Ответственный за приёмку» → «Приёмка»: каждый блок «Корректен» → «Принять панель v1».
4. Роль «Инженер запуска» → «Завершить этап»: «Объект готов к эксплуатации»; «Протокол» → «Скачать PDF».

**Блокировка → исправление → повторная проверка**: `/objects/obj-002/history` – этап 1 заблокирован (история за 19 из
24 месяцев, недостающие месяцы перечислены, следующее действие – «получить полную выгрузку») → «Полная история» →
автоматическая повторная проверка снимает блокировку → «Аудит» воспроизводит статус на момент до исправления.

**Все 11 сценариев ТЗ**: `/scenarios` → «Запустить все» – статусы считает приложение, ожидаемые значения только
для сравнения. Подробно – [docs/demo.md](docs/demo.md).

## Известные ограничения

- **Этап 3 – только имитатор.** Реальные команды оборудованию не отправляются (требование ТЗ); реальные
  `setpoint_sent/received` из `telemetry.csv` анализируются на этапе 2.
- **Роли в демо-режиме выбираются в меню профиля.** Вход обязателен только при `AUTH_REQUIRED=1`; SSO нет.
- **Пороги проверок – параметры демонстрации** из ТЗ и паспорта (99 %, 30 мин, 5 с, 60 с, пауза 10 с, допуск
  2 кВт · 3 %); для другого класса объектов нужна новая версия набора правил.
- **Ручное время проверки не измерено** – метрика «сокращение медианного времени ≥ 30 %» показывается как «не
  измерено» до замера инженером (инструмент на `/scenarios`).
- **Протокол – PDF без электронной подписи**, формируется в браузере.
- **`Configuration_file.json`** хранится, но не обрабатывается; объяснения через LLM не реализованы (по ТЗ – опционально).
- **Docker-образ локально не собирался** (на машине разработки нет Docker) – проверяется в GitHub Actions.
- **Допущения по реальному набору** (окно истории, пустые значения последних суток, событийные сигналы управления)
  перечислены в [docs/limitations.md](docs/limitations.md) – их нужно подтвердить у кейсодержателей.

## Безопасность и данные

- Реальные команды оборудованию невозможны: единственный транспорт – имитатор, движок отклоняет любой другой (`UnsafeTransportError`).
- Паролей, API-ключей, токенов и учётных данных в репозитории и логах нет: пароль базы – только в `.env`
  (не коммитится), сессии – HttpOnly-cookie, в базе хранится хэш токена, пароли сотрудников – scrypt.
- Реальных персональных данных и закрытых данных компании в репозитории нет: набор кейса и документы ТЗ
  (`public/case4`, `docs/source`) в `.gitignore` и не попадают в образ (ТЗ 4.3); в тестах – синтетические EAN и вымышленные контакты.
- Обязательные проверки нельзя обойти через интерфейс: переходы выполняет конечный автомат, права ролей проверяются в движке.
  Устаревшее подтверждение обновляется только после повторной проверки на текущих данных.
- Вкладка с устаревшим состоянием не затирает свежее: запись несёт ревизию, сервер отклоняет чужую (409).
- Текст во входных данных – только данные: он не влияет на статусы и не исполняется (сценарий 10).
- Локальные копии данных кейса удаляются в течение 7 дней после хакатона (ТЗ 4.3 п. 8).
